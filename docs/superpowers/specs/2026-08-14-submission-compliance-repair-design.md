# 最终提交确定性问题修复设计

## 目标

在不改变现有 L1–L5 满分运行行为的前提下，修复提交仓库中已经确认的合规、跨平台复现、文档一致性和打包问题。

## 明确不在本轮修改的内容

- 不修改现有程序化抓取、BC 恢复、导航或放置行为。
- 不修改主办方禁止修改的 `app.py`、`knowledge/task_config.json`、`src/robot_agent/core/`、`src/robot_agent/environments/`。
- `skills/` 直接访问 MuJoCo 的问题保留为“待主办方书面确认”的风险项，不宣称已解决。
- 不改写五题原始成功轨迹、评分和结果文件中的历史数据。

## 修复设计

### 1. 官方基准与受保护资源

以修复时主办方 `master` 的明确提交哈希为审计基准，补齐提交仓库缺少的五个上游文件。大文件继续使用 Git LFS。重新生成受保护边界审计 JSON 和 Markdown，报告必须明确区分逐字节一致文件、正确实体化的 LFS 文件、缺失项和允许范围内的新增项。

### 2. Windows 验证与 LFS 诊断

所有 JSON 文本使用 UTF-8 读取。验证脚本在计算模型哈希前识别 Git LFS 指针，并给出 `git lfs pull` 的可执行提示。验证输出应分别报告模型、证据、模型路由和受保护边界结果。

### 3. 文档单一事实来源

根目录 README、技术报告、实验开发日志、复现指南、最终提交清单和排行榜草稿统一使用最终成绩、时间、团队名、Issue #13、仓库地址和同一审计基准。实验开发日志中的旧结论保留为有明确日期和“历史阶段”标签的过程记录，文件开头给出最终状态，避免评委误读。

### 4. 训练复现边界

28 份历史训练配置不再依赖特定电脑盘符。配置中的数据目录和输出目录改成相对项目根目录的路径。新增训练数据清单，记录最终模型所需数据文件、预期相对位置、是否随 Git 提交和缺失时的处理方式。文档准确说明：最终推理可复现；从头训练仅在取得清单中的 HDF5 后可复现。

### 5. 证据可移植性

原始 evidence JSON 作为不可变历史证据保留。新增相对路径证据索引，供评委定位仓库内的 score、result、trajectory 和模型，不修改原始评分记录中的 Mac 绝对路径。

### 6. 跨平台提交 ZIP

重新生成 ZIP，不包含 `__MACOSX`、`.DS_Store`、AppleDouble 文件或 Git LFS 指针模型。目录和文件名采用 ASCII，ZIP 条目使用 UTF-8。压缩包只包含提交说明、技术文档、GitHub 地址和五条成功轨迹；代码与真实模型由 Git clone + Git LFS 获取。

## 验证

- Python 和 JSON 语法检查通过。
- Windows 兼容验证脚本在 UTF-8 环境及模拟中文系统编码条件下均能读取文件。
- 28 份训练配置不存在 `D:\\`、`E:\\` 或 `/Users/` 绝对路径。
- Git LFS 完整性检查通过，远端不存在待推送模型对象。
- 新 ZIP 不含 Mac 元数据，文件名 UTF-8 标志正确，五条轨迹 JSON 可解析。
- 受保护文件与选定官方提交一致；若上游 LFS 对象确实不可取得，报告必须如实列为缺失，不能写“缺失 0”。
- 当前五份历史满分证据仍为 10、15、20、25、30，总分 100。
